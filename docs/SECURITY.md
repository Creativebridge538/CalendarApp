# セキュリティ対策の状況

このアプリは複数の店舗（会社）の実業務データ（シフト・売上・報酬）を預かるSaaSとして設計している。「バグがないシステムです」とは言わない方針で、代わりに「何を実際に検証したか」をここに残す。

## 実施済み

### データ分離（テナント分離）

- アプリ層: 全16テーブルでRow Level Security（RLS）を有効化。店舗をまたいだ参照・更新は`store_id`ベースのポリシーで拒否される（詳細は[`PERMISSIONS.md`](PERMISSIONS.md)）
- インフラ層: 案件（会社）ごとに独立したVercelプロジェクト＋独立したSupabaseプロジェクトを払い出す（[`DEPLOYMENT.md`](DEPLOYMENT.md)）。アプリ層の分離が万一破られても、そもそもDBが物理的に別

### 権限昇格の防止

`public.users`のRLS更新ポリシーは行単位の制御しか持たず、列単位（どの列を変更できるか）は制御していなかった。これにより一般キャストが自分自身の`role`列を直接APIで`admin`に書き換えられる不具合を検証環境で確認し、修正済み（`20260812060000_lock_privileged_user_columns.sql`）。`role`/`store_id`/`reward_rate`/`is_active`は、本人が自分の行を更新する場合に限りDBトリガーで変更前の値に戻される。

### ダブルブッキング防止

同じ店舗・同じルームで時間帯が重なる`confirmed`シフトを、DBのEXCLUDE制約（`shifts_no_double_booking`）で拒否する（`20260812050000_prevent_double_booking.sql`）。以前は管理画面のタイムライン表示上での事後警告のみで、同時操作や直接APIコールを防げていなかった。

### サーバー側での権限再検証

全ての管理者専用ページ・APIルートは、クライアント側の表示制御だけでなくサーバー側（Server Component / Route Handler）でロールを再確認してから処理する。

### 自動テスト

`tests/rls/security.test.ts`（`pnpm test:security`）で、以下を実際にPostgREST層に対して実行し証明している:

- キャスト間・店舗間のデータ分離（読み取り・更新）
- 上記の権限昇格防止トリガー
- キャストが自分のシフトを直接確定できないこと
- キャストが自分の修正申請を自分で承認できないこと
- ダブルブッキング制約の動作（重なる場合は拒否、重ならない場合・日またぎは許可）
- 管理者による正規の他ユーザー編集が壊れていないこと（回帰確認）

## 未対応（要対応、優先度順）

| # | 項目 | 状態 |
|---|---|---|
| 1 | エラー監視（Sentry等） | 未導入。本番のJS/API/DBエラーを追う手段が現状ない |
| 2 | `real_name`/`phone`のキャスト自己編集をRLS/トリガーで禁止 | UI導線はないがAPIレベルでは制限なし |
| 3 | バックアップ・復旧手順の明文化と復元リハーサル | Supabaseのプラン依存の自動バックアップに乗っているのみ |
| 4 | 認証・シフト提出・報酬計算などの主要フローの自動テスト | RLS/セキュリティ観点のテストのみで、機能の正しさを担保する回帰テストはまだ薄い |
| 5 | `organization_id`概念の導入 | 現状は「1店舗＝1テナント」前提。本部・複数店舗を持つ会社に対応する場合は再設計が必要 |

## セキュリティ上の判断で意識していること

- RLSは「行単位」の制御であり「列単位」ではない。自己更新を許可するテーブルでは、権限に関わる列が紛れ込んでいないか個別に確認する（`users`で一度実際に穴があった）
- DB制約で表現できる business rule（ダブルブッキング等）は、UI側の警告表示だけに頼らずDBレベルで強制する
- 新しい制約を追加する際は、必ず既存データとの矛盾を先に確認してから適用する（矛盾があるとマイグレーションが失敗する）
